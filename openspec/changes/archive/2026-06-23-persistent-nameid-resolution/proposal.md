## Why

Today, when a service provider requests `nameid_format: persistent`,
the bridge returns the upstream OIDC `sub` claim (or the user's email)
as the NameID. That value is neither opaque, pairwise, nor stable
under admin reconfiguration of `oidc_claim_mappings`, which violates
the SAML 2.0 contract for persistent identifiers and the Phase 2
requirement [FR-3][reqs] in
`docs/requirement/per-sp-attribute-mapping-v2-requirements.md`.
Enterprise SPs that key user records on the persistent NameID will
silently mis-link accounts the moment an operator tweaks their claim
mapping.

This is the second slice of Phase 2 (per [v2 design §9][design],
"Phase 2b") and unblocks the remaining work — the custom assertion
maker, the admin GET/PUT/DELETE endpoints, and the CLI unification —
all of which assume a working persistent NameID.

## What Changes

- Introduce a `persistent_nameids` table keyed by
  `(entity_id, user_subject)` with a UUID `persistent_id` column,
  `created_at` timestamp, and a foreign key to
  `service_providers(entity_id)` with `ON DELETE CASCADE`.
- Add a `PersistentNameIDRepository` with a single `GetOrCreate`
  operation backed by an atomic upsert, plus a Postgres
  implementation under `internal/repository/postgres/`.
- Replace the current `getNameIDValue` (which returns
  `attrs.Subject` / `attrs.Email`) with a context-aware
  `resolveNameID` step inside `MappingService` that:
  - Reads the canonical user identifier from
    `session.RawOIDCClaims["sub"]`, **never** from the mapped
    `UserAttributes.Subject`.
  - For `persistent`, looks up or creates the opaque ID via the
    repository.
  - **Fails closed** when the canonical subject is empty or the
    repository call fails — `ApplyMapping` propagates the error
    instead of falling back to a user attribute.
- **BREAKING (pre-production only)**: Service providers currently
  registered with `nameid_format: persistent` will receive
  brand-new opaque NameIDs on their next authentication. Any
  pre-existing account linkage in dev/demo SPs becomes orphaned.
  Production is unaffected (project is pre-production per [NFR-1][reqs]).
- Add structured logging and a tracing span at the resolution and
  repository sites to satisfy [NFR-4][reqs] (observability) — INFO on
  resolved persistent ID, DEBUG on format selection, span
  `repo.persistent_nameid.get_or_create`.
- Wire `PersistentNameIDRepo` into `internal/app/app.go` and pass it
  to `service.NewMappingService(...)`.

The field-clearing default-attribute suppression, the custom
`SPAssertionMaker`, the admin GET/PUT/DELETE endpoints, the
cross-map semantic validation, and the `--nameid-format` CLI removal
are explicitly **not** part of this change.

## Capabilities

### New Capabilities

None — this change extends the existing `per-sp-attribute-mapping`
capability with new requirements; no new capability surface is
introduced.

### Modified Capabilities

- `per-sp-attribute-mapping`: adds a "Persistent NameID resolution"
  requirement that defines opaque, pairwise, durable identifiers and
  fail-closed semantics; documents the canonical-subject lookup key;
  and tightens the existing implicit `transient`/`emailAddress`
  behavior with explicit scenarios.

## Impact

**Code**

- `migrations/003_add_persistent_nameids.sql` — new Goose migration
  creating the table with the cascade FK and primary key.
- `internal/repository/interfaces.go` — new
  `PersistentNameIDRepository` interface plus `//go:generate`
  directive.
- `internal/repository/postgres/persistent_nameid.go` — new file
  implementing the atomic `INSERT ... ON CONFLICT ... DO UPDATE ...
  RETURNING persistent_id` upsert under a tracing span.
- `internal/service/interfaces.go` — `MappingService` interface
  unchanged in shape; constructor in
  `internal/service/attribute_mapping.go` gains a
  `PersistentNameIDRepository` parameter.
- `internal/service/attribute_mapping.go` — replace `getNameIDValue`
  with `resolveNameID`; extract canonical subject from
  `RawOIDCClaims["sub"]` in `ApplyMapping`; propagate errors from
  the persistent branch.
- `internal/app/app.go` — construct `PersistentNameIDRepo` from the
  pool/tracer and inject it into `NewMappingService`.
- `mocks/mock_persistent_nameid_repository.go` — generated by
  `make generate`. `mock_mapping_service.go` is unchanged because the
  `MappingService` interface itself does not gain methods.
- `internal/service/attribute_mapping_test.go` — update fixtures so
  the persistent path uses the new mock and asserts fail-closed
  behavior; replace the existing "persistent returns subject" test.

**Persistence**

- New table `persistent_nameids`. Storage cost is negligible
  (one row per `(SP, user)` pair). The `ON DELETE CASCADE` keeps the
  table garbage-free when SPs are removed via direct DB operation,
  per [NFR-6][reqs]; user-lifecycle cleanup remains explicitly out of
  scope.

**Operational**

- Dev, staging, and demo environments will issue new persistent
  NameIDs to mapped SPs on first authentication after rollout.
  Operators who care about identity continuity in those environments
  must re-link SP-side accounts.
- Rolling forward is one Goose migration. Rolling back drops the
  table cleanly (no rows reference it from outside).

**Out of scope (deferred to later changes)**

- Custom `SPAssertionMaker` and removal of the field-clearing
  workaround (Phase 2c, FR-6).
- Admin GET/PUT/DELETE endpoints for SP attribute mapping
  (Phase 2d, FR-4 / FR-5).
- Cross-map semantic validation between `oidc_claim_mappings` and
  `saml_attribute_mappings` (FR-7).
- Unifying the `sp add` CLI on `--attribute-mapping-file` and
  removing `--nameid-format` (Phase 2e, FR-8).
- Periodic cleanup of `persistent_nameids` rows for upstream-deleted
  users (intentionally out of scope per [v2 §7 Out of Scope][reqs]).

## Non-goals

- Defining or enforcing user-lifecycle awareness in the bridge.
  Persistent NameID rows for users that disappear from the upstream
  OIDC provider remain inert in the database; no cleanup hook is
  introduced.
- Adding admin-facing read or update APIs for persistent NameIDs.
  The table is a private implementation detail of the mapping
  service.
- Changing the `transient` or `emailAddress` resolution behavior
  beyond making it explicit in the spec.
- Introducing a Postgres integration test harness if one does not
  already exist; integration coverage is best-effort within the
  existing harness and may be deferred to a follow-up change if no
  harness lands here.

## Success Metrics

- For a fixed `(SP, user)` pair, 100 consecutive authentications
  return the same NameID value, observable via assertion XML
  inspection.
- Two distinct SPs authenticating the same upstream user receive
  two distinct NameID values.
- Every NameID emitted with `nameid_format: persistent` parses as a
  RFC 4122 UUID and contains no substring of the user's `sub`,
  `email`, or display name.
- When the OIDC `sub` claim is absent or the database is
  unavailable, `ApplyMapping` returns a typed error and no SAML
  response is emitted (no silent fallback in logs or assertions).
- Tracing shows a `repo.persistent_nameid.get_or_create` span on
  every persistent-format authentication, and structured logs
  contain an INFO event per resolution with `entityID` and
  `canonicalSubject` keys.
